# DR32 — Move Drum Rack clone with 32 pads

Design spec. Date: 2026-07-25. Status: **draft, pending PROBE32 device result.**

Working name `dr32` / "Drum Rack 32". Repo `schwung-dr32/`.

---

## 1. Goal

A Schwung `sound_generator` module that is a faithful clone of Move's native **Drum Rack**
(16 × Drum Sampler / `drumCell`), extended to **32 pads**, that **loads Move's own
`.ablpreset` files** directly from the device library — and, if the device permits, writes
them back.

Two consumers, both first-class:

- **Standalone module.** Loads a kit, plays notes 36–67, edits pads on the OLED. Works with
  no other module present.
- **davebox.** davebox can browse/load kits into the module and edit pad params from its own
  UI, so sequencing and kit-editing stop being two disconnected worlds.

### Non-goals (this phase)

- The rack-level **insert FX** and **send FX** (`saturator`, `reverb`, …). Their parameters
  are parsed and round-trip preserved but **inert** — see §7 phase 2.
- Sample recording/resampling (that's Espy's job).
- Melodic Sampler, Drift, Wavetable.

---

## 2. Verified format facts

All confirmed by reading a real preset off the device
(`/data/UserData/UserLibrary/Track Presets/MD-1/Full Kits/MD1Kit13.ablpreset`, 56 KB JSON)
and cross-checked against the Move manual pp. 47–49 and the Live 12 Drum Sampler reference.

### 2.1 File shape

```
{ "$schema": "http://tech.ableton.com/schema/song/1.4.7/devicePreset.json",
  "kind": "instrumentRack", "name": "MD1Kit13",
  "parameters": { Enabled, Macro0..Macro7 },        // Macro0 may be {value, customName}
  "chains": [ { name, color, devices: [
      { "kind": "drumRack", parameters:{Enabled,Macro0..7},
        "chains": [ …16 pad chains… ],
        "returnChains": [ { devices:[ {kind:"reverb", parameters:{…}} ] } ] },
      { "kind": "saturator", parameters:{…} }        // the rack-wide insert FX
  ] } ] }
```

A **pad chain**:

```
{ "name": "", "color": 10,
  "mixer": { pan, volume, "solo-cue", speakerOn, sends:[{isEnabled, amount}] },
  "drumZoneSettings": { "receivingNote": 36, "sendingNote": 60, "chokeGroup": null },
  "devices": [ { "kind": "drumCell", parameters: {…}, deviceData: { sampleUri } } ] }
```

- `receivingNote` 36…51 in native kits — this is the **pad↔note map**, and it is per-chain
  data, not positional. Chains are not necessarily sorted by note (MD1Kit13 has 46/47 swapped).
- `sendingNote` (60) is what the cell's sample is pitched relative to.
- `chokeGroup`: `null` or a group id — pads in a group cut each other off.
- `mixer.volume` is **dB** (3.5 = +3.5 dB), `pan` −1…1, one send (`amount` in dB, −70 = off).
- `deviceData.sampleUri` = `ableton:/user-library/Samples/Preset%20Samples/Cheetah_BD1.wav`
  → URL-decode, map `ableton:/user-library` → `/data/UserData/UserLibrary`.

### 2.2 drumCell parameters (the engine contract)

Exact JSON keys observed, grouped, with the manual's semantics:

**Corpus-mined facts** (888 presets pulled off the device; 140 are drum kits = 2272 cells):

- Every native kit has **exactly 16 chains**. `Effect_Type` spellings observed:
  `Stretch` (2108), `8-bit` (74 — **lowercase b**), `Punch` (12), `Sub Osc` (8), `Noise` (4),
  `FM` (2). The exact strings matter for round-trip.
- **112 pads are empty** (`sampleUri: null`) — an empty pad is normal, not an error.
- `Voice_PitchToEnvelopeModulation` is **absent** from 896 of 2208 cells. Params are
  legitimately optional; a parser that assumes every key exists throws on real files, and a
  writer that helpfully adds missing keys silently rewrites 56 of the 140 kits.
- Cells carry **both** `Volume` (dB, −12…0 observed) and `Voice_Gain` (linear), plus `Pan`.
- `Voice_Envelope_Hold` tops out at exactly **60.0** across the whole corpus.

**Voice / sample**
| Key | Meaning | Range |
|---|---|---|
| `Voice_PlaybackStart` | start point, fraction of sample | 0…1 |
| `Voice_PlaybackLength` | played region, fraction | 0…1 |
| `Voice_Transpose` | semitones (int) | −48…48 |
| `Voice_Detune` | cents | −50…50 |
| `Voice_Gain` | linear gain (1.0 = unity) | −70…24 dB equiv |
| `Voice_VelocityToVolume` | vel→vol depth | 0…1 |
| `Voice_PitchToEnvelopeModulation` | "Envelope Follows Pitch" | bool |
| `NotePitchBend` | per-note PB enable | bool |
| `Pan`, `Enabled` | | |

**Envelope (AHD)**
| Key | Meaning |
|---|---|
| `Voice_Envelope_Mode` | **`"A-H-D"`** = manual's *Trigger*, **`"A-S-R"`** = *Gate*. ✅ verified (extending-move's Gate Kit example) |
| `Voice_Envelope_Attack` | seconds (1e-4 min) |
| `Voice_Envelope_Hold` | seconds; **`60.0` is the `inf` sentinel** ✅ verified (Choke Kit uses 60.0 for whole-sample playback; corpus max is exactly 60) |
| `Voice_Envelope_Decay` | seconds |

**Filter**
| Key | Meaning |
|---|---|
| `Voice_Filter_On` | bool |
| `Voice_Filter_Type` | `Lowpass` (12/24 dB), Highpass 24, Peak — need to confirm how 12 vs 24 is encoded (see §9 O2) |
| `Voice_Filter_Frequency` | Hz |
| `Voice_Filter_Resonance` | 0…1 |
| `Voice_Filter_PeakGain` | peak-type gain |

**Modulation (one slot)**
`Voice_ModulationSource` ∈ {Velocity, Slide} · `Voice_ModulationTarget` ∈ {Filter, Attack,
Hold, Decay, FX1, FX2} · `Voice_ModulationAmount` bipolar.

**Playback Effect** — `Effect_On` + `Effect_Type` ∈ nine values, each using two of these keys:

| Type | Param 1 | Param 2 |
|---|---|---|
| `Stretch` | `Effect_StretchFactor` | `Effect_StretchGrainSize` (s) |
| `Loop` | `Effect_LoopOffset` | `Effect_LoopLength` |
| Pitch Env | `Effect_PitchEnvelopeAmount` (−1…1) | `Effect_PitchEnvelopeDecay` (s) |
| `Punch` | `Effect_PunchAmount` | `Effect_PunchTime` |
| 8-Bit | `Effect_EightBitResamplingRate` (Hz) | `Effect_EightBitFilterDecay` |
| `FM` | `Effect_FmAmount` | `Effect_FmFrequency` (Hz) |
| Ring Mod | `Effect_RingModAmount` | `Effect_RingModFrequency` (Hz) |
| `Sub Osc` | `Effect_SubOscAmount` | `Effect_SubOscFrequency` (30–120 Hz) |
| Noise | `Effect_NoiseAmount` | `Effect_NoiseFrequency` (colour) |

**All nine effects' params are always present in the JSON regardless of `Effect_Type`** — so a
lossless round-trip is easy: keep the whole param dict, overlay the ones we model.

Per the Live manual: time/frequency controls in Stretch, Loop, FM, Ring Mod, Sub Osc and Noise
**track the played note and the global pitch controls** — i.e. these are note-relative, not
absolute. That is a fidelity requirement, not a detail.

### 2.3 Samples

`Preset Samples/`: 1339 files, 216 MB. Sampled header (`Cheetah_BD1.wav`): RIFF PCM,
**mono, 44100 Hz, 24-bit**. Host audio is 44100 Hz / 128-frame stereo blocks — so **no
resampling is needed for playback at unity pitch**; only transposition resamples. The loader
must still handle 16-bit and stereo (user samples).

Whole user Samples tree = 3.8 GB, so **never scan-and-cache everything**; resolve lazily.

## 3. Pad model — **flat 32, decided by PROBE32** ✅

`PROBE32.ablpreset` (MD1Kit13 extended to 32 chains, receivingNotes 36–67, upper 16
transposed +12 st) was loaded on the device 2026-07-25. Result:

- Native Move **loads it fine** — no error, no refusal, no crash.
- The lower 16 pads behave completely normally.
- Chains 17–32 are simply **not reachable** on a native drum track (there's no way to address
  more than 16 notes there) — but their presence is harmless.

**Decision: one flat 32-chain list, notes 36–67, written into a single native-legal
`.ablpreset`.** No sidecar, no bank split, no second file format. A DR32 kit opens on native
Move as an ordinary 16-pad kit; DR32 sees all 32. A native 16-pad kit loads into DR32 with
pads 17–32 empty.

**Open follow-up (non-blocking, O8):** does native Move *preserve* chains 17–32 if the user
re-saves the preset from the device? Almost certainly not — a native re-save probably rewrites
16 chains and silently drops the extension. That's an acceptable, explainable failure mode
("edit DR32 kits in DR32"), but it needs confirming so the manual can say so plainly.

**Pad grid.** Move's surface is 4×8 = 32 pads, and native Drum Rack uses only the left 4×4.
DR32 uses the full 4×8 as one 32-pad kit. Bottom-left pad = note 36, matching native layout
convention, ascending in rows of 4.

## 4. Architecture

```
schwung-dr32/
  module.json            component_type: sound_generator, chainable
  dsp/
    dr32.c               plugin v2 entry, param dispatch, state
    dr32_voice.c/.h      one drumCell voice: sample playback + AHD + filter + FX
    dr32_effects.c/.h    the nine playback effects
    wav.c/.h             WAV loader (16/24-bit, mono/stereo) — from schwung-waveform-editor
    dr32_kit.c/.h        kit model: 32 pads, note map, choke groups, mixer
  ui/
    ui.js                entry: init + MIDI dispatch + globals
    ui_*.mjs             pad grid, param banks, browser, canvas editor
  lib/
    ablpreset.mjs        ← the shared parser/serializer (canonical home, see §6)
  tests/                 off-device C harness (davebox pattern: tests/run.sh)
  tools/                 render_canvas.mjs preview, kit dumper
```

**Split of duty.** JS does file I/O, browsing, preset parse/serialize and UI; C does audio and
holds the live kit. Kit transfer JS→DSP is a flat param set: `pad<N>_<key>` writes plus a
`pad<N>_sample` path string that the DSP loads **off the audio thread** (load request queue +
worker; audio thread only ever sees an atomically-swapped ready buffer). This is the one hard
real-time rule: **no file I/O, no malloc, no logging on the audio thread**
(cf. the davebox RT-logging footgun).

**Voices.** 32 pads × N voices. Native Drum Rack is one voice per pad with retrigger (a pad
cuts itself off) plus choke groups across pads. Start there; make the per-pad voice count a
build constant so a "poly pad" option is cheap later. Budget check: 32 simultaneous
24-bit→float mono voices with a 2-pole/4-pole filter and one effect each is well inside the
~21 %-of-a-core envelope echidna measured, but this gets benched (§7 M1 exit).

**Sample memory.** Preload whole samples to float32 RAM at load time. A 32-pad kit of typical
Move one-shots ≈ 32 × ~30 KB × (32/24 bit expansion) ≈ a few MB — fine. Guard with a
per-kit ceiling (say 64 MB) and refuse/trim beyond it rather than OOM the device.

## 5. UI

- **Pad grid**: 4×8, pads light by chain `color`, hit = play + select.
- **Param banks** mirroring the manual exactly, so muscle memory transfers:
  **Main Bank** — Transpose · Attack · Hold · Decay · Playback Effect · FX param 1 · FX param 2
  (manual shows "Sub Amount / Sub Frequency" because the type was Sub Osc — the last two
  encoders are the *selected effect's* two params).
  **Filter & Setup** — Filter Frequency · Resonance · Filter Type · Envelope Mode · Choke ·
  Velocity→(target) · Velocity→Vol · Pan.
  Bank switch: wheel, as native.
- **Canvas kit editor** (`type: "canvas"`) via **schwung-canvaskit** — the 128×64 editor
  showing the pad grid, sample names, and the selected pad's params. Per the canvaskit memory:
  DR32 keeps its own `src/canvas.config.js` and **commits the generated `canvas.js`**; it
  generates at whatever canvaskit version is current *at that time* and stays there. No fleet
  regen.
- **Kit browser**: file browser rooted at `/data/UserData/UserLibrary/Track Presets`, filtered
  to `.ablpreset`, with a **content check for `"drumRack"`** — this is exactly the bug class
  the movy `mrdrums` plan hit (unfiltered browse → load garbage → crash). Reject with a toast,
  don't crash.
- ⚠ **SHIFT is CC 49** and reaches canvas `onMidi` (memory: `schwung-canvas-shift-cc49`), and
  the host **eats Shift+Step13 / Shift+Vol combos** before a module ever sees them
  (`schwung-host-reserves-shift-step-combos`). Pick shortcuts accordingly.

## 6. The shared `.ablpreset` library

`lib/ablpreset.mjs` — **canonical home is this repo**; davebox vendors a *copy*. Not a live
dependency, no fleet updates, no back-compat shims (the canvaskit doctrine, applied).

API:

```js
parseKit(jsonText) -> { name, pads: [{ note, sendingNote, chokeGroup, color,
                                       mixer:{volume,pan,send}, sampleUri, samplePath,
                                       params:{…drumCell params…} }],
                        rackFx: {...}, sendFx: {...}, _raw }
serializeKit(kit)  -> jsonText     // writes back into _raw, preserving every unknown key
resolveUri(uri)    -> absolute path            // ableton:/user-library → /data/UserData/UserLibrary
toUri(path)        -> ableton: uri
isDrumKit(jsonText) -> bool                    // the "drumRack" content check
```

`_raw` + write-through is what makes lossless round-trip possible: DR32 only ever *overlays*
the fields it models onto the original document, so unmodelled FX params, macro mappings and
future schema fields survive a save untouched.

**davebox uses it for:** pad labels in the sequencer grid (real sample names on drum tracks),
choke-group display, and the kit browse/load and per-pad-edit control path (§8) — including
when davebox is driving Move's *native* Drum Rack rather than DR32.

## 7. Milestones

**M0 — probe & decide.** PROBE32 ✅ flat 32 (§3). Parser + lossless writer ✅ —
`lib/ablpreset.mjs` round-trips **140/140 device kits byte-exact** (`tests/roundtrip.mjs`).
Write-back probe `DR32WB.ablpreset` deployed to the device, awaiting a native load. Remaining:
O2 filter-type craft, O4 effect param units, O8 native-re-save behavior.

**M1 — playable core.** WAV loader; 32-voice engine with sample playback, `Voice_*` params,
AHD envelope both modes, the filter, the one mod slot, mixer vol/pan, choke groups, note map.
Parser loads real kits. Pads + both param banks on the OLED.
*Exit:* MD1Kit13 loads and — by ear and by null-ish comparison against the native rack playing
the same kit — sounds right; `bench_render`-style CPU number recorded.

**M2 — the nine playback effects.** Each modelled against the manual's described behavior, and
each verified against native Move rendering the same pad. Note-tracking of time/frequency
params (§2.2) is part of the acceptance, not a follow-up.

**M3 — kit editing + save.** Edit pads, save kits (native `.ablpreset` per M0 result), kit
browser, canvas editor.

**M4 — davebox integration.** Control channel: kit browse/load + per-pad param edit + pad
labels. Vendored `ablpreset.mjs` copy into davebox.

**Phase 2 (post-1.0) — rack FX.** Port the Move FX models (saturator, reverb, delay,
chorus-ensemble, phaser-flanger, redux, channel EQ, dynamics, auto filter) so a Track Preset
sounds complete. Until then their params ride along untouched in `_raw`.

## 8. davebox integration

Confirmed scope: **browse/load kits from davebox** and **per-pad param edit from davebox**.

DR32 is a `sound_generator` in a Schwung slot; davebox is a `tool`. They need a control
channel that is *not* the MIDI note path. Options to settle in M4 (needs a look at what the
host offers today — `chain_params` writes from another module, a shared state file under
`/data/UserData/schwung/`, or a small SHM mailbox like the inject ring):

- **Preferred if it exists:** davebox writes DR32's chain params through the host's existing
  slot-param API — no new IPC, and it also gives the remote UI the same power for free.
- **Fallback:** a versioned JSON mailbox file + a poll on DR32's UI tick (cheap, ~11 Hz, and
  the tick is already there). Slower but zero host changes — and *zero host changes is the
  point*, given the host-protection rule.

Either way the wire format is "pad index + param key + value", the same vocabulary as
`ablpreset.mjs`, so davebox never learns a second dialect.

**Note routing.** davebox sequences DR32 by sending notes 36–67 on the slot's receive channel
(`docs/ADDRESSING_MOVE_SYNTHS.md` — module out channel = slot receive channel). Nothing
special needed; DR32 just has to honour the full 36–67 range and velocity.

## 9. Open questions / risks

- **O1 — PROBE32.** ✅ Resolved 2026-07-25: flat 32 (§3).
- **O8 — native re-save drops pads 17–32?** See §3. Non-blocking; confirm before the manual
  makes any claim about editing DR32 kits on native Move.
- **O2 — Filter type encoding. STILL OPEN — needs one device craft (Josh's hands).** All 2208
  corpus cells say `Voice_Filter_Type: "Lowpass"`, so the corpus can't answer it. Mining
  `/opt/move/MoveOriginal` turned up the *display* strings — `Low-Pass 12dB`, `Low-Pass 24dB`,
  `High-Pass 24dB`, `Notch`, `Lowpass 12dB` — which are UI labels, not the JSON enum values,
  and there's no slope key anywhere in the cell param set. **Resolution:** set a pad's Filter
  Type to each non-default value on the device, save the preset, diff the JSON. ~2 minutes,
  and it's the last thing blocking exact filter modelling. Not blocking M1 start (LP is the
  default and covers the entire corpus).
- **O3 — `Hold = inf`.** ✅ Resolved: the sentinel is **60.0 s**, no separate flag.
- **O9 — `Volume` vs `Voice_Gain`.** Cells carry both (dB and linear). Which one the pad's
  Volume encoder actually drives, and whether they multiply, needs one device craft.
- **O10 — `extending-move`'s schemas are NOT authoritative.** `static/schemas/drumRack_schema.json`
  on the device looks like a spec but is **generated by observation**
  (`utility-scripts/generate_additional_schemas.py`) from a handful of presets — `min == max`
  on nearly every field gives it away. Use it as corroboration only; it did independently
  confirm the `A-H-D` / `A-S-R` enum. Do not lift its ranges into the engine.
- **O4 — Effect param units.** `Effect_StretchGrainSize: 0.0999` — seconds or a normalized
  0…1? Determined by sweeping the param on-device and diffing, per the same method. Applies to
  every effect param before M2 modelling starts.
- **O5 — Stretch quality.** Move's Stretch is a granular time-stretch; matching its artifact
  character (the manual explicitly sells the "granular lo-fi texture") is the hardest single
  fidelity target in M2. Budget real time for it.
- ~~**O6 — Module count cap.**~~ Not a risk: `MAX_MODULES=64` truncation is **cosmetic only**
  (Help-menu listing + analytics census); the FX picker and Tools menu each do their own
  `readdir` and bypass `module_manager`, so DR32 will launch normally regardless
  (`_worklogs/OUTSTANDING.md`, 07-21).
- **O7 — Licensing.** Everything reused must be MIT (waveform-editor, filter lib). Do **not**
  pull from `move-anything-dj` (CC BY-NC-SA, viral) — same constraint Espy documented.

## 10. Method notes

- Every engine constant gets **measured against the device**, not guessed — the standing
  fidelity directive. The instrument here is the same one that worked on Typhon: **craft a
  preset on the device, read the JSON back, diff.** It bypasses every CC-route trap.
- The off-device C test harness (davebox `tests/run.sh` pattern) is the first-line check for
  envelope/filter/effect logic; on-device verification still gates "done".
